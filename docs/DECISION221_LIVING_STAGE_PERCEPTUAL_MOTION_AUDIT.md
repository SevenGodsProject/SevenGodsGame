## 2. なぜ 4.22% が知覚されなかったか（定量＋知覚の説明）

| # | 要因 | 数値 |
|---|---|---|
| 1 | **描画されていない**（測定枠の誤り） | 実効カバー率 0.0%（preview 幅・全スマホ）／3.3〜4.0%（PC 768 以上） |
| 2 | 残った分も UI と減光の下 | 左右最下隅。敵立ち絵（x 15–27%）と OTOMO（x 83–89%）に隣接、減光 α 0.27〜0.45 の帯 |
| 3 | **静止した参照エッジがない** | 一様な波テクスチャの内部で帯が流れるだけ。運動知覚は「静止した輪郭に対する相対運動」で最も強く、テクスチャ内部の低コントラスト運動は最も弱い |
| 4 | 空間周波数が周辺視に合わない | 帯幅 48〜104px（≒ 0.7〜1.5°）の細かい縞。周辺視は**低い空間周波数・大面積**に感度が高く、細かい縞はほぼ見えない |
| 5 | 速度が検出閾値付近 | 6〜10 px/s ≒ 0.1〜0.2°/s。低コントラストでは周辺視の運動検出閾値（数 °/s）を下回る |
| 6 | 注意の競合 | すぐ隣で敵/神/OTOMO の立ち絵・HUD・ダメージ数字が動く。周辺視の注意は動的な UI に奪われる |

補足の実証：既存の `.battle-arena-glow` は**すでに arena 全面**で 9 秒周期・opacity 0.5↔0.8 の呼吸をしているが（`battle.css` L144-168）、誰も「背景が生きている」とは感じていない。全面・低コントラスト（±3% 程度）・構造に紐づかない呼吸は「生命感」にならない、という**下限の証拠**である。

**決定220 の設計上の誤り（AI 側）**：カバー率・振幅・継ぎ目はすべて **canonical 画像の座標系**で検証し、**実際にレンダリングされる arena の座標系**で検証しなかった。決定219 の「禁止領域」定義も同じ座標系だったため、この誤りは 219 から引き継がれた。

## 3. 「背景が生きている」と知覚されるための仮説（カバー率）

前提：ふつうに戦闘している視線は 神（中央）↔ 敵（左）↔ 手札（下）を往復し、背景は常に周辺視で見られる。

| 条件 | 仮説値 | 根拠 |
|---|---|---|
| 実効カバー率（UI に隠れない arena 比） | **≥ 25%**（決定220 は 0〜4%） | 周辺視は大面積・低空間周波数の輝度変化に感度が高い。全面 ±3%（arena-glow）は不感 → 面積だけでなく §3 の他条件が要る |
| 分布 | 視線の**左右両側**に ≥ 2 領域、うち 1 つは神の背後〜上（中央上） | 片側の隅だけでは、視線が反対側にある間は見えない |
| 参照エッジ | 各領域が**固定された輪郭**（月の縁・龍の輪郭・灯籠）に接する | 相対運動／相対輝度変化として知覚させる |
| 空間周波数 | 領域サイズ ≥ arena 幅の 12%（≒ 4° 以上） | 周辺視の感度帯域 |
| 時間周波数 | 0.05〜0.12 Hz（8〜20 秒周期）、複数位相 | 遅すぎると変化に気づかず（決定220）、速いと戦闘の邪魔 |
| 振幅 | 対象領域で **+6〜10% luma**（arena-glow の 2〜3 倍） | 下限証拠（±3% 不感）と可読性の上限の間 |
| Human QA 成立条件 | 探させない・教えない・ブラインド ON/OFF | §9 |

この仮説は Narrow Pilot で検証する対象であり、確定値ではない。

## 5. 推奨方式（1 案）：「照明レイヤー」— 月・龍・灯籠の光が呼吸するステージ

### C-1. 概念
このステージは「月光の下で龍神が顕現している宮」。**動くのは光**である：
- **月暈**（月盤の外側の空・雲）が 14 秒周期でゆっくり明滅（+0 → +8% luma）
- **龍のオーラ**（龍の輪郭の内外 60px の帯と龍本体の輝度）が 11 秒周期で脈動（+0 → +7%）
- **灯籠の暖光**（8 基、半径 90px）が 7〜9 秒の互いに素な周期で微かに揺らぐ（+0 → +6%、暖色）
- 位相はすべて異なるため、全体としては 1 周期のない「息づき」になる

**動かさないもの**：龍・神殿・階段・鳥居・石床・灯籠・建築・水域・月盤の**形・位置・内容**。カメラ・ズーム・パララックス・粒子は使わない。

### C-2. 【CEO DECISION REQUIRED】固定物の「輝度」を呼吸させてよいか
- Issue：決定220 の絶対条件は「固定物の画素を置き換えない」だった。照明レイヤーは固定物の**画素の明るさ**を最大 +6〜8% 変化させる（形・位置・内容・色相は不変、暗くはしない）
- AI Recommendation：**承認**。「固定＝形・位置・内容の固定。照明（輝度）の緩やかな呼吸は可、上限 +8% luma、加算のみ」に規約を改める
- Reason：§1-4 の通り、見えている背景の 8〜9 割が固定物。画素完全固定のまま動かせる面積は 4〜7% で、決定220 と同じ結果になる（§4）。照明は絵の identity（構図・シルエット・色）を変えない
- Alternatives：①画素完全固定を維持 → 実効 4〜7%、NO-GO（静止のまま）。②雲だけ動かす → 3.4〜7.5%、HUD の裏、却下。③H3 動画 → 決定219 で否決
- Risk：明滅が強すぎると「背景が気になる」。上限 +8% と Human QA のブラインド判定で制御する
- Impact if delayed：Living Background の全構想が停止（静止背景を採用して次の課題へ進む）
- CEO Action：承認 / 拒否

### D. motion 対象領域（canonical 座標）
| 領域 | 位置 | 役割 |
|---|---|---|
| 月暈 | 中心 (0.61, 0.11)、r 118〜300px の環 | 中央上・全 viewport で見える主刺激 |
| 龍のオーラ＋龍本体の輝度 | x < 0.40, y < 0.48 | 左側（敵の背後）の刺激 |
| 灯籠の暖光 ×8 | 各灯籠中心 r 90px | 小面積だが周辺視のフリッカー感度が高い、左右下段 |
| （任意）自由な空の薄い雲ヴェール | y < 0.44 の非構造領域 | ＋数%、月暈と連続させる |

### E. 想定 motion coverage
実効カバー率（UI に隠れない arena 比）**PC 23〜39%／SP 25%**（§4 表）。決定220 の 0〜4% に対し 6〜10 倍。§3 の仮説「≥ 25%・左右両側・参照エッジあり」を満たす。

### F. canonical preservation
- canonical ファイルは無変更・1 ピクセルも置き換えない（決定220 と同じ構造）。
- 照明フットプリントを 1 枚の **alpha マスク**（canonical 座標・`mask-size: cover; mask-position: center top` で背景と自動整合）にし、その内側だけに**加算**（`screen` / `plus-lighter`）。暗くなる方向の変化は構造的に不可能。
- ガード：+8% luma 上限（決定220 と同じオフライン再現で全フレーム検証）、色相不変（加算色は月＝冷白、灯籠＝暖色に限定）。
- 検証項目（決定220 と同じ手順を**arena 座標系で**行う）：①viewport 別の実効カバー率 ②固定物の最大輝度変化 ③形状変化 0（差分は輝度成分のみ） ④継ぎ目なし ⑤reduced-motion で完全停止。

### G. performance 予算
| 項目 | 予算 |
|---|---|
| JS／フレーム | 0（CSS アニメーションのみ） |
| 合成レイヤー | ≤ 3（月暈 1・龍 1・灯籠 1。transform/opacity のみ、`filter` 不使用） |
| レイヤー面積 | 各 ≤ 1.2 × arena（決定220 の張り出しの教訓：固定長） |
| GPU メモリ | ≤ 12MB @1240×743 |
| 追加アセット | マスク 1 枚（≤ 20KB WebP）。動画・canvas・WebGL なし |
| mobile | 幅 < 600px は**月暈のみ**（灯籠は HUD の裏、龍は左端外）。60fps はコンポジタのみで担保 |
| reduced-motion | 層ごと `display: none`（静止画と同一） |

### H. Narrow Pilot を作る価値
- **C-2 承認の場合：YES**。実効 25〜39% は仮説 §3 を検証できる最小構成で、コストは決定220 と同等（CSS ≈ 90 行・マスク 1 枚・TSX 0 行）。
- **C-2 拒否の場合：NO**。画素完全固定で残る 4〜7% は決定220 の再現になる。**静止背景を採用し、Living Background を CLOSE する**方がゲームとして正しい。

### I. 作る場合の最小変更
1. `public/assets/backgrounds/stages/06-dragon-ocean-light-mask.webp`（新規 1 枚。月暈・龍・灯籠のフットプリント）
2. `battle.css` 末尾：決定220 ブロックを照明レイヤーに**置き換え**（≈ 90 行。水域ブロックは削除）
3. `BattleScreen.tsx`：**変更 0**（既存の `data-living-stage` と `.battle-living`、`?living=off` をそのまま使う）
4. 決定220 の水域マスク（未 commit・untracked）は削除（明示パス）
5. Gate を実装前に固定：実効カバー率 ≥ 25%（PC 1366×768 で測定）／固定物の輝度変化 ≤ +8%／形状差分 0／継ぎ目 0／reduced-motion 停止／全テスト PASS／`src/core` 差分 0

### J. Human QA 成功条件（「探す」ではなく「感じる」）
- 事前に**動く場所を教えない**。CEO は通常どおり 1 戦（7 ラウンド）プレイする。
- ブラインド ON/OFF：`/`（ON）と `/?living=off`（OFF）を AI が順序をランダムにして 2 戦提示し、CEO は「どちらが生きていたか」を答える。
- 成功 = ①正しく識別できる ②終了後の質問「背景は静止画だったか」に「生きていた／息づいていた」と答える ③「背景の方が気になった」＝ No ④カード・敵の予告・HP の可読性に不満なし。
- 失敗 = ①で識別不能、または③が Yes。どちらでも数値追加調整による救済はしない（決定220 と同じ扱い）。
- QA 前に CEO の viewport（`window.innerWidth × innerHeight`）を記録し、§1 の表の該当行で実効カバー率を確定させる。
