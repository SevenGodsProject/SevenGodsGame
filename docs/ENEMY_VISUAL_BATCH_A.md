## 3. Export Spec（実際に使った設定）

```
source（透過 PNG・本体高さ 1302〜1446px）
  → 本体の最大連結成分 bbox を抽出
  → 現行 asset の本体寸法 × 1.5（= 768/512）へ Lanczos3 で縮小
  → 768×768 の透過キャンバスの、現行 asset と同じ位置（× 1.5）へ配置
  → WebP quality 90 / alphaQuality 100 / effort 6
  → 可逆 PNG 参照と比べて PSNR ≥ 33dB（監査の受け入れ基準）を満たさない場合のみ品質を上げる
```

| enemy | canvas | 採用 quality | 可逆参照との PSNR / SSIM |
| --- | --- | --- | --- |
| datenshi | 512→768 | **q90** | 36.08dB / 0.9991 |
| karakuri | 512→768 | **q90** | 33.31dB / 0.9992 |

doukeshi だけ q90 では 32.56dB と基準を 0.44dB 下回ったため、基準を満たす最小品質として q94 を採用した（q92 は未達）。容量は +23KB。**これが監査仕様からの唯一の逸脱**で、理由は「監査自身が定めた受け入れ基準 ≥33dB を満たすため」。

**1 を下回る条件の正体（重要・正直に記録する）**

- 数値は Laplacian variance（二階微分のエネルギー）で、**シャープ処理のハローに強く反応する**。旧 asset は書き出し時にシャープが掛かっており（監査：輪郭比 1.59〜2.75）、その人工的な縁取りが数値を押し上げていた。今回はそれを足していないので、条件によっては数値が下がる。
- 実画素を 4〜5 倍に拡大して目視した結果、**PC1366 DPR1 でも After の方が細部（鎧の唐草・歯車の歯・鎖）は明確に解像している**。下がっているのは「作られたコントラスト」であって情報量ではない。
- Chromium は `background-image` の縮小に mipmap 系のフィルタを使うため、**縮小率が mip 段（768→384→192）の中間に落ちる条件ほど軟らかくなる**。768px は 194px 表示（≒mip 192）と 570px 表示（≒768 の 0.74 倍）では有利、285px 表示（384 と 192 の中間）では不利という、今回の数値の並びとちょうど一致する。
- Mobile は datenshi / doukeshi が中立〜わずかに軟らかく、karakuri は明確に改善。**Mobile の本質的な問題は「敵が小さいこと」（列幅 124〜190 CSS px）で、これは画質ではなくレイアウト側の課題**（決定173 でも別 Phase として整理済み）。

→ 対処として「軽いシャープを足す」ことは **CEO の禁止事項**なので行っていない。mip 段に合わせた canvas 寸法の再選定は Batch C の検討候補として §12 に記載した。

**敵の顔との重なりについて**：この指標は `.enemy-avatar` の外形矩形の上 40% を「顔」とみなして callout との重なりを取るもので、**画像の中身は一切参照しない**（`play.mjs:65`）。`.enemy-avatar` は `enemy-idle` アニメーションで常時わずかに動いているため、callout を採取した瞬間の位相で値が変わる。実際、同じ戦い（#6 才華×乱舞の道化）が Before 43 → After run1 0 → After run2 162 と振れており、決定170 でも「同一ビルドで 0 / 48 / 21+45px² に振れる。再実行なしに回帰と見なすな」と記録済み。敵要素ボックスは 56 条件すべてで 0px 差なので、**Batch A が幾何を変えた可能性はない**。

→ 結論：**6-C は悪化していない**。再現する非ゼロ値はゼロ件。
