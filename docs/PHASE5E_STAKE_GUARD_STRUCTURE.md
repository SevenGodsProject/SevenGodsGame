# Phase 5-E — 神階の「受け構造」設計比較監査（実装なし）

Phase 5-D（決定157）で残った3課題（god spread 36pt／機工師16%・魔獣22%／大技ラウンドの加護使用率47%）を、
**加護そのものを強くするのではなく神階側の受け構造で**改善できるかを、本番コードを変えずに比較した記録。
成果物はこの文書と `scripts/phase5e-guard-structure/structureAudit.test.ts`（`P5E_RUN=1`）。決定158 は未記録。

---

## 0. 結論

| 項目 | 結論 |
|---|---|
| 推奨 | **B：加護だけ神階Ⅳ以降のブロック効率0.75の対象外にする**（神託回数は4回のまま） |
| A（神託4→5） | **不採用**。神階Ⅶ 51→63%、全神階 +3〜+12pt で難易度の帯（45〜55%）を大きく外れる。直すには神階の敵側数値を再び締める必要があり、Phase 5-B をやり直すことになる |
| C（A+B） | **不採用**。神階Ⅶ 68%。予告を読む方策では99%・spread 2 で差がつかない |
| D（条件付き回復） | **比較せず**。B が帯の中で福永・大耀・魔獣を動かせたので、新ルールを足す理由がない |
| Phase 5-E を実装すべきか | **実装すべき。ただし B ＋ gameVersion fingerprint の修正だけ**。神託回数には触らない |
| 残る課題 | 「大技が来た時点で神託残0」（開始時基準 41〜42%）は B では動かない。神託回数に手を入れずに解く手段は本比較の範囲に無く、Known Risk として残す |

最初に、5-D で仮置きした受入基準5「大技ラウンドの加護 60%以上」は**合理的なプレイヤーでは到達できない定義**だと分かった（§8）。
神階Ⅶの大技（予告100以上）の 54% は「受けてもHPが35%以上残る」安全な予告で、そこで加護を押すのは「とりあえず加護」そのもの。
危険な大技（受けた後 HP<35%）に限れば BASE で 78%、B で 85% になる。基準は「危険な大技で75%以上・安全な大技で30%以下」に置き換えることを勧める。

## 1. gameVersion fingerprint 監査（実装前の安全修正候補）

### 1-1. 現在の gameVersion に含まれているもの

`src/core/replay/gameVersion.ts`（Phase 4.6・決定140・commit `9f56e45`）。`"<engineVersion>.<dataFingerprint>"`。

| 部品 | 中身 | 更新 |
|---|---|---|
| `RULES.ranking.engineVersion` | reducer・スコア計算・RNG の**挙動**の版。現在 1 | 人が上げる。上げ忘れは golden replay（`gameVersion.test.ts`）が検出 |
| `dataFingerprint()` | `RULES`（`ranking` と `replay.pendingRuns` を除く）＋ `ALL_CARDS` ＋ `ENEMIES` ＋ `GODS` ＋ `OTOMOS` を `stableStringify` → FNV-1a×2（16進16桁） | データが1つでも変われば自動で変わる |

### 1-2. `DIVINATION_CHOICES` が除外されている理由

除外は**意図ではなく漏れ**と判断した。根拠：
* `rankingImpactSnapshot()` はデータモジュールを手で列挙している（rules / cards / enemies / gods / otomos）。`src/core/data/divination.ts` はこの列挙に無い
* 決定139・140 の本文に「神託／託宣」への言及は無い（除外理由が記録されていない）
* Phase 4.6 時点の加護・導き・天啓の数値（HP+3・ブロック+2・4ダメージ）は `divination.ts` の**リテラル**で、`RULES` に無かった。「調整値は rules.ts に集約」（不変ルール4）から外れていたため、`RULES` を指紋に含めても拾えなかった
* Phase 5-D で `RULES.divination.guardRatio / guardMin` を足したことで、加護の**数値**は指紋に入った。だが `DIVINATION_CHOICES` の**構造**（効果の種類・順番・導き／天啓の数値）は今も対象外

### 1-3. 指紋に足すべきもの

| 対象 | 判断 | 理由 |
|---|---|---|
| `DIVINATION_CHOICES`（`src/core/data/divination.ts`） | **足す**（`rankingImpactSnapshot()` に `divination: DIVINATION_CHOICES` を1行） | 対局結果に直接影響する。`text` も含めてよい（文言変更で版が変わっても害は無い。気にするなら `effects` だけを取り出す） |
| `STAKE_LEVELS` / `STAKE_CHOICES`（`stakes.ts`） | 不要 | 表示用。数値はすべて `RULES.stakes` から導出しているので既に指紋に入っている |
| `dailyStart.ts` | 不要 | `RULES.daily.modifier` を使うだけ（指紋に入っている） |
| `dailyBoss.ts` | 不要（注意点あり） | 週替わりの順番はアルゴリズム（コード）。`DAILY_BOSS_POOL` は `ENEMY_IDS` の定義順から作るので、**`ENEMY_IDS` の並びを変えると Daily の敵が変わるが指紋は変わらない**。並びを変える時は `engineVersion` を上げる |
| `decks.ts` / `deckBuilder.ts` | 不要 | デッキはリプレイ入力に明示的に入る |
| `cardArt.ts` | 不要 | 見た目のみ |

### 1-4. golden replay / Daily day-lock / saveVersion への影響

* **golden replay**：指紋に足すと `gameVersion` が変わる（`1.da1ec40838d7ff9a` → 新しい値）。固定操作列の決着は変わらないので、`GOLDEN.gameVersion` だけ更新する
* **golden の検出力の限界**：golden は Daily（神階0）で、加護1回・導き2回を使うが**天啓は使わない**。天啓だけを変えた場合や、神階でしか効かない挙動変更（候補B はまさにこれ）は golden では検出できない。B を実装するなら、神階Ⅳの固定リプレイをもう1本 golden に足すか、`intentGuard.test.ts` で神階Ⅳの値を固定する
* **Daily day-lock**：版が変わる deploy は **JST 0:00 直後**に行う。B と指紋修正は同じ deploy にまとめて、版の変更を1回にする
* **saveVersion**：影響なし。`gameVersion` はセーブに入らない（`runLog.formatVersion` とも独立）。A・B のどちらも `GameState` の形を変えない（A は `divination.remaining` の初期値、B はブロック量の計算）。**saveVersion 9 のまま**
* **B を実装したときの版の上げ方**：B の挙動を `RULES.divination` の真偽値（例 `guardIgnoresBlockEfficiency: true`）で切り替える形にすれば、**データ変更として指紋が自動で変わる**ので `engineVersion` の手動更新に頼らなくて済む（§10）

## 2. 比較の方法

* `scripts/phase5e-guard-structure/structureAudit.test.ts`。本番コードは触らず、ハーネス側で候補を再現する
  * **A**：`START_GAME` 直後に `divination.remaining` を 5 にする（本番では `RULES.stakes.divinationCount` の1値）
  * **B**：加護を使った直後に、効率で削られた分（raw − round(raw×0.75)）をブロックへ足し戻す（本番では `blockOfIntent` が `effectiveBlock` を通らない形）。ブロックは rng を使わないので決定論は崩れない
  * **C**：A＋B
* **paired seed**：4候補とも同じ seed 文字列。BASE は Phase 5-D の実測（Ⅶ 51%・神別・敵別・予告を読む方策 88%・加護 47/13/85%）と**完全に一致**することを確認してから使った
* **7神 × 7敵 × 神階Ⅰ〜Ⅶ**、seed 6（Ⅰ〜Ⅶの曲線）と seed 12（Ⅴ・Ⅶの詳細）
* **2つの方策**
  * **固定方策（STAKE-01）**：本番ゲートと同じ。blind・3戦略・神ごとに最良（Ⅶは3択の最良）。託宣は「defensive は常に加護、balanced は危険なら加護それ以外は天啓、aggressive は天啓」。加護の使用率はこの定義から機械的に決まる（致死100%・安全0%）ので、固定方策では**勝率と神託の残数**だけを見る
  * **予告を読む方策**：balanced・aware（条件を狙う）。託宣の機会ごとに 加護／導き／天啓／温存 の4通りを最後まで打ち切って比べ、最良を選ぶ。同点は加護以外を優先
* **定義**：大技＝予告100以上（`RULES.cardBonus.enemyBigThreshold`）。致死＝予告−現在ブロック≥HP。危険＝受けた後 HP<35%（方策の危険判定と同じ）
* **神託残数の定義の補正**：「大技が来た時点で神託残0」は**ラウンド開始時点**の残数で数える。5-D のハーネスはラウンド終了時点で数えており、「そのラウンドで最後の1回を使った」場合も切れ扱いになっていた。5-D の 57% は、正しい定義では **42%（予告を読む方策）／51%（固定 balanced）**。本文書はすべて開始時基準
* ノイズの目安：神別勝率（Ⅶ・最良戦略）は seed 6 で 42局、seed 12 で 84局 → 1局＝2.4pt／1.2pt。**5pt 未満の差は読まない**

## 8. 「大技時の加護 60%」という基準について

神階Ⅶ・予告を読む方策（BASE）の大技ラウンドの託宣判断 1,181 回のうち、**危険（受けた後HP<35%）は 540 回（46%）、安全は 641 回（54%）**。
安全な大技で加護を押す率は 19% で、残りは天啓（削り切り）か導きを選んでいる。これは合理的な判断で、ここを 60% に上げるには「安全でも加護」＝**基準10（とりあえず加護にしない）と矛盾**する。

| 定義 | BASE | B | 目標案 |
|---|---|---|---|
| 大技ラウンド全体での加護率（5-D 基準5） | 46% | 51% | （到達不能） |
| **危険な大技での加護率** | 78% | **85%** | **75%以上** |
| 安全な大技での加護率 | 19% | 18% | **30%以下** |
| 致死予告での加護率 | 86% | 92% | 85%以上 |

推奨：基準5 を「危険な大技で 75%以上・安全な大技で 30%以下」に置き換える。BASE が既に満たし、B はさらに良くなる。

## 9. 副作用

## 11. 候補ランキング（Impact × Frequency × Simplicity × Risk、各1〜5・Risk は安全なほど高い）

## 12. Phase 5-E を実装すべきか

**実装すべき。ただし範囲は B ＋ fingerprint 修正のみ。**

* B は Phase 5-D のゲームループ（予告を見る → 神託を使うか判断 → 残りを手札で解く）を変えずに、加護の価値と本文の数字を一致させる。使用率は「危険なときほど使う」方向に動き、通常ラウンドでは増えない
* A・C は難易度の帯を外れ、直すには神階の敵側数値をもう一度触ることになる（Phase 5-B の再実施）。「無料の手が増えた」効果であって受けの判断が増えたわけでもない
* B で解けないもの（神託残0 41%・機工師 18%）は Known Risk として明記し、次の Phase で神託回数と敵側の再センタリングを**セット**で扱うかを別途判断する

## 15. Known Risks（B を採った場合に残るもの）

1. **大技ラウンド開始時の神託残0 41%**：神託回数を触らない限り動かない。次Phaseで「神託 4→5 ＋ 神階の敵側再センタリング」をセットで検討するかは CEO 判断（stake 数値の変更を含む）

3. **寿楽 +2〜+5**：妨害で予告を削ったうえに加護が乗る。実装後に神別で再計測する
4. **神階Ⅶ 54%**：帯の上端。seed を増やして 55 を超えないことを実装時に確認する
5. **golden は B を検出しない**（Daily は神階0）：神階Ⅳの golden を足すまで、B の挙動変更は unit test でしか守られない
