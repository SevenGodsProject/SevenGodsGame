- 監査スクリプト：`scripts/enemy-visual-audit/{capture,metrics,encode,zoom,match-sources,match-sources-bg}.mjs`

## 1. Executive Summary

1. **敵 7 体は「2 世代」に分かれている。** datenshi・karakuri・doukeshi は 2026-08-23〜24 に個別生成された約 1,100〜1,480px の透過 PNG（塗りの細かい painterly）が source。oni・onryo・juuma・ryujin は 2026-08-04 に **1 枚のシート（1536×1024）** として生成され、`.NET System.Drawing` で 384×512／512×512 に切り出した絵（決定32）が唯一の source で、**ドット調・白フチ（alpha edge の白マット）・ジャギー** を元から持つ。
2. **「WebP 変換で輪郭が 30〜49% 劣化」は再現しなかった。** source を同寸に揃えて測ると、onryo／ryujin は PSNR 33dB・SSIM 0.999・輪郭エネルギー比 1.00（純粋な再エンコード）、oni は 35dB／0.72（q90 相当の圧縮による軟化 28%）。3 体（painterly）は現行 asset の方がクリーン縮小より輪郭エネルギーが **高い**（1.6〜2.8 倍＝書き出し時にシャープ処理が入っている）。つまり劣化の主因は変換ではない。
3. **juuma だけは変換工程で本当に劣化している。** source 本体 357×359px を Production では 428×432px へ **1.2 倍に拡大** して置いており、輪郭エネルギーが source の 38% に落ちている（ぼけ）。
4. **表示側の事実**：Production 戦闘画面の敵は PC 1366×768 で 285 css px（asset 512 の 0.557 倍）。DPR2 では **570 device px ＝ 512 asset を 1.11 倍に拡大** して描画しており、ここだけが「解像度不足」になる。PC 1508×660 は 194 css px、Mobile 390 幅は敵ごとに **125〜190 css px**（asset の 0.24〜0.37 倍）で、Mobile は画質より「小ささ」の問題。
5. **神との差**：神は 640px asset を 239 css px（0.373 倍）で表示、敵は 512px asset を 285 css px（0.557 倍）で表示。**敵は神の 1.5 倍の拡大率で見せている** ため、同じ画面で敵だけ甘く見える構造がある。加えて画風差（神＝チビ・セル調、painterly 敵、ドット調敵）が「世代が違って見える」印象を作る。
6. **推奨**：3 体は source から **768px・WebP q90（alphaQuality 100）** に再書き出し（合計 +236KB、asset 名維持・CSS 変更なし）。PC 1366 DPR2 での輪郭エネルギー +18〜21%、PC 1508 DPR2 で +30%。4 体は再書き出しでは改善しないため **再生成（painterly 世代に揃える）** を CEO 判断へ。juuma が最優先。

## 13. Recommended Export Spec（Production 採用候補・1 案）

```
enemy source（透過 PNG、本体高さ ≥ 700px）
  → 本体の最大連結成分 bbox を抽出（破片は落ちる）
  → 768×768 透過キャンバスに Production と同じ構図比で配置
     （本体高さ = 0.85 × 768 = 653px、中心 x・下端 y は現行 asset の比率を維持 → 画面上の位置・大きさは不変）
  → alpha 縁：縁の帯 1.5〜2.5px を確認、白マット（premultiplied 白フチ）が無いこと
  → sharp：webp({ quality: 90, alphaQuality: 100, effort: 6 })
  → asset 名は現行のまま上書き（art.webp / art_hq.webp）→ src・enemies.ts・CSS 変更なし
  → 受け入れ：PSNR ≥ 33dB（可逆参照比）、輪郭比 ≥ 0.98、alpha 完全性、Production 画面で scroll 0・6-B 実測不変
```

- onryo は現行と同じ縦長比（576×768）で書き出す（contain の描画幅を変えない）。
- 世代 A の 4 体は再生成後に同じ spec を適用。再生成前に「再エンコードだけ」を当てても改善しないので **行わない**。
- 512 のままの再書き出しは PC DPR2 で効果ゼロ（表 6）。1024 は +510KB で効果はあるが必要 device px（最大 570）を大きく超えるため「必要最小限」に反する。

## 16. Risks

| リスク | 内容 | 対策 |
| --- | --- | --- |
| 構図ずれ | 再書き出しで本体の位置・大きさが変わると 6-B の enemy plate・6-C callout の位置関係が動く | 構図比を現行 asset から数値で引き継ぐ（§13）。書き出し後に `phase6b-layout-audit/measure.mjs` と `phase6c` の overlap 実測を再走 |
| alpha 縁 | source の縁帯 4.5〜5.7px を 768 に縮めると 2.7〜3.4px。太すぎるとにじむ | 縁帯 ≤ 2.5px を受け入れ条件に |

| Mobile の小ささ | 画質を上げても 390px では 125 css px のまま | 本監査の対象外。6-B follow-up（列幅の固定）として別 Phase に切り出す |
| キャッシュ | asset 名維持で上書きすると CDN／ブラウザキャッシュに旧画像が残る | Vite は `public/` をハッシュ無しで配信するため、切替直後は混在しうる。Cache-Control は `max-age=0, must-revalidate` なので再訪で更新される |
