**結論：** 7神は「数値と見た目」では4神が区別できるが、「攻略思想・カード優先度・勝ち筋」では区別できない。手番中に神を意識して選択を変える理由は、現在のコード上ほぼ存在しない。

### 主要ファクト

1. **神本体に固有ルール（passive）が無い。** `GodDef` のロジック関連フィールドは `resonanceEffects`（BURST時効果）と `otomoId` のみ。HP・AP曲線・手札・共鳴上限・託宣は全神同一。カード効果の適用時に神IDを見る経路は無い（§3）。
2. **60カードは9種の無条件数値effectを1〜2個並べたもの。条件付き・連鎖・予告参照・シナジーeffectは0枚**。3効果以上のカードも0枚（§8-1）。
3. **どの神でも「ダメージ効率の高い札を撃つ」が最適。** 探索AIの使用率は攻撃札93〜99%（全神）、回復・ブロック札50〜80%。デッキ内価値（入れると勝率がどう変わるか）は 神託・渾身の一撃・大喝・乱舞・秘技満ちる が**全神でプラス**、回復・ブロック・軽量妨害札は**全神でマイナス**（§8-3）。
4. **防御という戦い方が成立していない。** 「fortress（自HP最優先）」プロファイルは7神全てで最下位〜下位。防御型の看板神・笑蓮は神階Ⅳで **rush（速攻）が balanced より+20.5pt**（§6-1）。蒼毘・笑蓮・寿楽の防御系専用カード（不動の構え／福袋／笑って許す／長生きの知恵 等）はデッキに入れると勝率が **−8〜−15pt**（§8-3）。
5. **BURSTは「試合に1回起きるかどうか」のイベント**（0.6〜1.3回／試合、初発動R3.5〜6.5）。OTOMOは実質 incarnate の効果1回のみで、doji は到達不能。神の唯一の固有効果が戦い方の軸になれていない（§5-2）。
6. **寿楽一強は再現**（神階Ⅶ：ヒューリスティック77.6〜79.8%、探索AI 94.6〜96.4%、他神はそれぞれ31〜65%／63〜93%）。分解結果：**寄与の第1位はおすすめデッキの共通12枚、第2位は「神階ATK倍率→デバフ定数減算」の順序、第3位はBURSTデバフ。OTOMOは寄与ほぼ0**（§7）。「寿楽が強い」より「寿楽のデッキと、デバフが神階に強い構造」が正確。

## 3. Current Architecture（God / Card / Effect / Resonance / OTOMO / simulation）

### 3-1. Effect システム（`src/core/types/effect.ts`, `engine/effects.ts`）

```
Effect =
  | damage(target, amount)   | block(amount)  | heal(amount)
  | resonance(amount)        | draw(amount)   | gainAp(amount)
  | buff/debuff(target, stat:'atk'|'def', amount, rounds)
  | score(amount)   ← BASE-D（決定109）で無効化済みの dead effect
```

- 全効果は **無条件・即時・固定値**。`condition` / `trigger` / 参照（敵intent・自HP・手札枚数・共鳴値・直前のカード）を表す構造は型に無い。
- `stat:'def'` は型にあるがデータも消費処理も無い（effect.ts コメントで明記済み）。
- 唯一の「時間を跨ぐ」効果は `buff/debuff atk`。プレイヤー atk バフはカードダメージに加算、敵 atk デバフは敵行動の合計から1回減算（連撃は先頭hitから消費）。
- 神・OTOMO・託宣・カードは全て同じ `Effect[]` を持ち `applyEffects` で順処理。**神IDで分岐する箇所はMastery集計（表示用）のみ。**

### 3-3. Resonance / BURST 経済

- ゲージmax 7、7到達で即BURST→0（超過は捨てられる）。共鳴を生むのはカード13枚（共通9＋専用4）のみ。
- BURST順序：OTOMO進化 → 神効果 → 進化後形態のOTOMO効果（spirit効果は構造上一度も発動しない）。
- doji は BURST 3回＝共鳴21が必要。おすすめデッキの共鳴総量は 7〜13（§8-1）で理論上も到達不能。
- Manual BURST は決定127で REJECT。本監査では再検討しない。

### 3-4. 神託（`data/divination.ts`）

3択固定（heal3+block2／draw1+gainAp1／damage4）、AP消費なし、1R1回、7回（神階では4回）。神差なし。

### 3-5. カード・デッキ・報酬

- 60枚＝共通32＋専用4×7。デッキ20枚、同名2枚まで。神プール＝共通32＋自神専用4＝36種。
- おすすめデッキ：恵比寿・蒼毘・才華・寿楽は手動固定（v4）、大耀・福永・笑蓮は種別比率の自動充填（笑蓮のみ専用1枚ずつ）。
- 報酬3択：勝利後にプール36種からseed決定論で3枚 → 選ぶとそのカードの編成上限+1のみ（カード効果は不変）。

### 3-6. Enemy Intent（`engine/round.ts`）と神階 modifier（`data/stakes.ts`）

- 敵は7R分のスクリプト表。予告は常に正確。プレイヤー側で予告を参照する効果は無く、読み合いは「ブロック量／デバフを当てるか」のみ。
- 神階：Ⅰ託宣4・R5以降ATK+20%・ATK+10%／Ⅱ初手−1／Ⅲ敵HP+10%／Ⅳブロック効率75%／Ⅴ回復効率60%／Ⅵ必殺・連撃+20%／Ⅶ選択。
- **敵ATK倍率は行動合計に乗算され、その後デバフが定数で減算される**（`multiplier`→`scaleEnemyAction`→`atkBuff`）。倍率が上がるほど「定数で削る」デバフの相対価値が増える（§7）。

### 3-7. 既存 simulation harness と本監査で追加した計測

- 既存 `balanceSim.test.ts`：3戦略ヒューリスティックAI。カード選択は「ブロック→回復→ダメージ効率順」で神IDを見ない → 「神でカード選択が変わるか」は測れない。
- 追加（`scripts/phase3-audit/`、分析専用）：
  - `harness.ts`：イベントから指標抽出（ダメージ構成／block／heal／draw／AP／デバフ実効量／BURST回数・R／OTOMO形態／託宣R／カード使用率）。既存3戦略AIの移植＋**探索AI**（1R内の全手順を予算付き全探索し、敵ターンまで先読みして「価値関数＝プロファイル」で評価。rush／balanced／fortress／resonance／engine／control の6種）
  - `static.audit.ts`／`baseline.audit.ts`／`playstyle.audit.ts`／`juraku.audit.ts`（出力は `out/*.md|json`）

- 「最良プロファイルが balanced を **5pt以上** 上回り、かつ他神と異なる」神は **神階Ⅶで0／7、神階Ⅳで1／7（笑蓮＝rush）**。プロファイル順位相関（Spearman）の平均は神階Ⅳ 0.19・Ⅶ 0.37 と低いが、これは勝率差が数試合分しかなく順位がノイズで入れ替わるためで、差別化の証拠ではない。

- **resonance（BURST優先）は神を問わず有効**。BURSTは「神の個性」ではなく「全員が同じように得をする共通ボーナス」として機能している。

### 6-2. 独自指標の定義（初心者向け説明）

- **プロファイル**＝AIの「性格」。rush は敵HPを減らすことを最優先、fortress は自分のHPを守ることを最優先、resonance は共鳴ゲージを溜めることを最優先……と6種類用意し、同じデッキ・同じ敵で戦わせた。
- もし神ごとに個性があれば「蒼毘は fortress が一番勝てる」「才華は engine が一番勝てる」のように**最良の性格が神ごとに変わる**はず。実測では、ほぼ全神で balanced／resonance が最良で、変わらなかった。
- **最良−balanced**＝「その神らしい戦い方をしたときの上乗せ」。5pt以上あれば「意識して戦い方を変える価値がある」と判定。現状は最大+4.5pt（蒼毘・Ⅶ）。

### 7-5. Root Cause 候補（寿楽、寄与順）

1. **おすすめデッキの共通12枚**（3AP火力札4枚＋2APデバフ札4枚。火力総量7神最大・専用札は2枚ずつ8枚）— 他神に渡すと+6〜30pt

3. **BURSTデバフ（atk−6×3R）**— ヒューリスティックで−8pt、探索AIでは0
4. **OTOMO（寿鹿）**— 寄与±2pt、ほぼ無関係
5. **敵の攻撃形式**（連撃・複数回攻撃の敵が7体中5体で、定数減算が刺さる）

**したがって「寿楽nerf」は誤った処方。** 寿楽の数値を下げても、同じデッキを組める他神（J5）との差は残らず、神階での防御神不利も直らない。是正対象は (a) おすすめデッキの設計基準の統一、(b) 神階Ⅳ・Ⅴの効率modifier vs デバフの非対称、の2点で、いずれも Step 2 で設計比較する（本Stepでは変更しない）。
